# Four gameplay bug fixes: doors, collisions, and terrain sizing

This change fixes four independent bugs: rental doors on different floors triggering interaction, garage doors sinking into the ground instead of rising, door frame objects blocking passage with their merged bounding box, and terrain size resetting to 200 when importing maps in the editor. Each fix is small and targeted. The door frame collision approach introduces a new `hasCustomColliders` flag that splits the collision contract into "use everything" (default) vs "use only invisible meshes" — a clean opt-in that avoids regressing existing objects.

**Watch for:** The `addColliders` material visibility check uses a type assertion to `MeshBasicMaterial` that may silently pass for merged `MeshStandardMaterial` meshes (confirmed). The rental door Y-filter still uses 3D `distanceTo` for the range check, so a door at Y+2.4m eats into the effective horizontal range (confirmed, minor).

## High-level view

The rental door fix adds a Y-distance early-exit in `findNearest`, rejecting doors more than 2.5m above or below the player before the 3D range check runs. This prevents a door on floor 2 from appearing interactive to a player on floor 1.

The garage door fix is a one-character sign change: `closedPos.y - doorHeight` becomes `closedPos.y + doorHeight`. The door now rises upward instead of sinking below the ground plane.

Door frame collision is the most structurally interesting fix. `mergeGroup` merges same-material meshes into a single geometry, and `addColliders` computes one bounding box for that merged mesh — which for a door frame spans the entire opening. The fix adds invisible meshes at each pillar/lintel position, sets `userData.hasCustomColliders = true`, and modifies `addColliders` to only process invisible meshes when that flag is present. `mergeGroup` already preserves invisible meshes separately, so the pipeline is compatible.

The terrain size fix addresses MapEditor always constructing TerrainSystem at 200x64 regardless of map data. `importData` now checks whether the imported size/resolution differs and calls `resize` first. `importMap` emits `onTerrainResized` and rebuilds the grid helper to keep the UI synchronized.

## Rental door Y-axis proximity filter

```typescript
if (Math.abs(position.y - door.closedPosition.y) > 2.5) continue;
```

This prevents a rental door on floor 2 (at Y=4m) from registering as within 3m of a player on floor 1 (at Y=0) when positioned directly below it. The remaining `distanceTo` call is still 3D. For a door at exactly Y=2.4m offset (just under the threshold), the Pythagorean tax means the effective horizontal range shrinks to ~sqrt(9 - 5.76) = ~1.8m. On ramps or split-level designs a player could be within obvious XZ reach and still fail to interact. Switching to XZ-only distance after the Y-filter would eliminate this edge case.

## Door frame collision meshes and the hasCustomColliders protocol

The root cause: `mergeGroup` merges all meshes sharing the same material into a single geometry. For `door_frame`, the two metal pillars at x=-0.6 and x=0.6 (both using `M.metalDark`) get merged into one mesh whose bounding box spans from x=-0.66 to x=+0.66 — completely blocking the 1.2m opening.

The fix introduces a two-part protocol:

1. **EditorObjects** adds invisible collision meshes (one per solid element) with `new THREE.MeshBasicMaterial({ visible: false })`, then sets `g.userData.hasCustomColliders = true`.
2. **PlaytestMode's `addColliders`** checks the flag and, when set, skips all visible meshes and only generates Box3 colliders from the invisible ones.

`mergeGroup` already separates invisible meshes from the merge pass and preserves them as individual children. So after merging, the group contains merged visible meshes (for rendering) plus individual invisible meshes (for collision).

The type assertion `(child.material as THREE.MeshBasicMaterial).visible !== false` works because `visible` is defined on `THREE.Material`, the base class. But the cast to `MeshBasicMaterial` is misleading — after `mergeGroup`, visible meshes use `MeshStandardMaterial`. A cast to `THREE.Material` would be clearer and more robust against tooling that might narrow type access.

## Terrain size on map import

MapEditor constructs TerrainSystem with hardcoded size=200, resolution=64. When importing a map built at size=400 (resolution=96), the old `importData` would write 9216 height values into a geometry with only 4096 vertices — silently corrupting the buffer.

```typescript
if (data.size !== this.size || data.resolution !== this.resolution) {
  this.resize(data.size, data.resolution);
}
```

In `importMap`, the grid helper is rebuilt to match the new terrain size and `onTerrainResized` is emitted so the React UI updates the terrain size dropdown. Without this callback, the editor UI would show "200" after importing a 400m map, and subsequent resize operations would use stale state.

The grid helper re-creation removes the old helper from the scene but does not call `.dispose()` on its geometry/material. This leaks GPU resources on repeated imports.

## Test coverage

Not tested: runtime collision behavior with these changes; the terrain resize path when going from a larger to a smaller terrain; the interaction between `hasCustomColliders` and objects that have invisible meshes but lack the flag.
