# Terminal UI rewrite: desktop/cameras/doors views with garage door lock system

The change replaces the terminal overlay in GameUI with a three-view system (desktop, cameras, doors) styled after Windows 95. It adds a `GarageDoorSystem` instance to `Game.ts`, wires navigation callbacks through `App.tsx`, and fixes five reported bugs: camera view not appearing on selection, missing lock-status color indicators, Russian watermark replaced with English "JailBreak", a taskbar showing the active app, and a 3-column scrollable camera grid. The approach threads garage-door lock state from a new system class through React state to the doors view, and connects camera selection to the existing `CameraSystem.openCamerasApp()` flow that starts screenshot capture.

**Watch for:** The `GarageDoorSystem` in `Game.ts` has no registered doors, so lock/unlock actions update UI state but have no physical effect on the 3D world (confirmed). Any team — including prisoners — can lock and unlock doors from the terminal because there is no authorization check (confirmed). The `new Date().toLocaleTimeString()` call in every taskbar renders on every frame the terminal is open, creating avoidable GC pressure (confirmed).

## High-level view

The camera-view bug fix works by routing desktop icon clicks through `openCamerasApp()`, which starts the screenshot capture interval. Previously, entering the camera grid bypassed this call, so thumbnails never rendered. The desktop->cameras indirection ensures `captureScreenshots()` fires before the grid appears.

`GarageDoorSystem` is instantiated in `Game.ts` purely as a state machine for the lock indicator UI. Unlike `PlaytestMode` (which calls `registerDoor` from map objects), `Game.ts` never registers any physical doors. The lock/unlock/tempLock methods mutate internal state and emit callbacks, but no meshes animate.

Terminal access is intentionally unrestricted — the comment in `Game.ts` says "Any team (guard or prisoner) can use security terminals." The cameras view is read-only, but the doors view exposes lock/unlock actions to prisoners with no team check. Currently cosmetic because no doors are registered, but will break gameplay once physical doors exist.

<summary>Issues (4)</summary>

1. **GarageDoorSystem has no registered doors** — `Game.ts` creates a `GarageDoorSystem` but never calls `registerDoor`. Lock/unlock actions change UI state only; no 3D doors respond. Either register doors from `PrisonMapDetailed` or document that this panel is decorative until map doors exist.
2. **No team-based access control on door lock actions** — prisoners can lock/unlock garage doors from the terminal. Add a guard-only gate in `Game.lockGarageDoors()`/`unlockGarageDoors()`/`tempLockGarageDoors()` or hide the doors icon for non-guards.
3. **Date construction on every render** — each taskbar calls `new Date().toLocaleTimeString(...)` inline. In React, this runs on every re-render. Memoize or update on a 1-second interval to avoid repeated allocations during gameplay.
4. **Taskbar duplicated three times** — the desktop, cameras, and doors views each contain a nearly identical 15-line taskbar block. Extract a `<Taskbar activeApp={...} />` component to reduce duplication and make future changes single-site.

## GarageDoorSystem as a headless state machine

`Game.ts` creates the system and hooks its callback but never registers doors:

```ts
this.garageDoorSystem = new GarageDoorSystem();
this.garageDoorSystem.onLockStateChange = (state) => {
  this.onGarageDoorLockUpdate?.(state);
};
```

In `PlaytestMode`, doors are registered by iterating map objects:

```ts
const gDoor = this.garageDoorSystem.registerDoor(garageDoorId, obj, doorPos, doorHeight);
```

Without registered doors, `update(delta)` lerps nothing, `canInteract()` always returns `{ canInteract: false, door: null }`, and the toggle logic is unreachable. The UI indicators will animate correctly (green/red/amber dots, countdown timer), but no mesh in the scene responds.

## Terminal access and authorization gap

The cameras view is read-only — prisoner access to surveillance is a deliberate gameplay decision per the code comment. The doors view, however, exposes `onLockGarageDoors`, `onUnlockGarageDoors`, and `onTempLockGarageDoors` with no team check. The three `Game.ts` methods pass through to `GarageDoorSystem` unconditionally:

```ts
lockGarageDoors() {
  this.garageDoorSystem.lockDoors();
}
```

Once doors are registered and locking actually blocks passage, prisoners controlling door locks would break gameplay. The fix: add `if (this.currentTeam !== 'guard') return;` in each method, or conditionally render the doors icon only when `team === 'guard'`.

## `new Date()` in render path

Each of the three taskbar instances contains:

```tsx
{new Date().toLocaleTimeString('ru-RU', { hour: '2-digit', minute: '2-digit' })}
```

While the terminal is open, `CameraSystem` emits state every second (screenshot interval), triggering re-renders. Each render allocates a `Date` and runs locale formatting three times. A `useState` + `setInterval` pattern would update the clock once per second without per-render allocation, and extracting the taskbar into a component would consolidate all three instances.
