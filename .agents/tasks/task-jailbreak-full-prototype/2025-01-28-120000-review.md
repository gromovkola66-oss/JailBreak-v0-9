# JailBreak singleplayer prototype: 18 scripts for full game loop

A complete CS 1.6-style JailBreak game prototype built from 18 C# scripts targeting Unity 6.4 URP. The codebase implements an FPS controller, 6 weapons with melee/ranged mechanics, a team/round lifecycle, AI bots with waypoint patrol and LOS combat, a door system, and full OnGUI HUD — all wired together by a single Editor menu button that builds the entire scene from primitives. The type system is internally consistent (all referenced enums, interfaces, and classes exist across files), and the scripts use New Input System and URP materials throughout.

**Watch for:** SpectateCamera.Start() calls `gameObject.SetActive(false)`, making it unfindable by `FindFirstObjectByType` — spectate mode will never activate on player death (confirmed). RoundManager.RestartRound() re-enters WaitingForTeamSelect but never shows the TeamSelectUI, so the game soft-locks after round 1 (confirmed). The kill feed in HealthSystem.Die() reports the *victim's* current weapon rather than the attacker's weapon (confirmed). BotController fires through walls when detection raycast finds a target but a subsequent fire raycast hits a different collider (likely).

## High-level view

The editor script (`JailBreakEditor.cs`) acts as a complete scene factory — geometry, MonoBehaviours, and cross-references all wired in code. The structural gap is that no script explicitly wires `DoorButton` to the cell `DoorController` instances; cell doors open reactively by polling `RoundManager.cellsOpen`, which works but means the button is cosmetic and the round manager is the actual authority.

The damage pipeline flows from WeaponController/BotController through DamageReceiver to HealthSystem/BotHealth. Friendly-fire prevention lives in DamageReceiver, weapon team restrictions in WeaponController.CanUseWeapon(). The gap is that `HealthSystem.Die()` queries `FindFirstObjectByType<WeaponController>()` to get the weapon name for the kill feed, which always returns the *player's* weapon controller — bot-on-bot or bot-on-player kills report the wrong weapon.

Round lifecycle has a state machine (WaitingForTeamSelect → PreRound → Active → PostRound → WaitingForTeamSelect). The transition back to WaitingForTeamSelect doesn't invoke `TeamSelectUI.Show()`, so after round 1 the player is stuck with no UI and no way to trigger `StartRound()` again.

The weapon system checks team restriction at fire time but not at switch time — a prisoner can cycle to slot 3 (AK-47) and see the model, just not fire it.

## SpectateCamera unreachable via FindFirstObjectByType

```csharp
// SpectateCamera.Start():
gameObject.SetActive(false);
```

Unity's `FindFirstObjectByType<T>()` skips inactive GameObjects. When the player dies, `PlayerController.SetDead()` calls:

```csharp
SpectateCamera spectate = FindFirstObjectByType<SpectateCamera>();
```

This returns null because the SpectateCamera GameObject is inactive. The spectate camera never enables. Fix: keep the GameObject active but disable only the Camera component (which the script already does with `spectateCamera.enabled = false`). Remove the `gameObject.SetActive(false)` line — the `isActive` flag already gates Update.

## Round restart soft-lock

`RoundManager.RestartRound()` transitions state to `WaitingForTeamSelect` and respawns entities, but nothing triggers `TeamSelectUI.Show()`. The TeamSelectUI starts with `isVisible = true` which handles the first round. After round 1 ends, `isVisible` remains false and the menu never reappears. The player has a locked cursor, no team selection, and no way to start the next round.

## Kill feed weapon attribution

```csharp
// In HealthSystem.Die():
WeaponController wc = FindFirstObjectByType<WeaponController>();
string weaponName = wc != null && wc.GetCurrentWeapon() != null ? wc.GetCurrentWeapon().weaponName : "Unknown";
```

This always finds the player's WeaponController (the only one in the scene). When a bot kills another bot or the player, the kill feed shows whatever weapon the *player* is currently holding. Bots fire with a flat `damage` field and have no weapon name to attribute. The fix is to pass weapon name through the damage chain: `DamageReceiver.TakeDamage(float, string attackerName, Team, string weaponName)` → `BotHealth.TakeDamage(float, string, string)` → `KillFeed.AddKill(...)`.

## Bot detection vs. fire raycast divergence

Detection (in `DetectEnemies`) fires a ray from `transform.position + Vector3.up * 1.5f` toward the target with a `+0.5f` Y nudge on the direction vector. The actual fire (in `FireAtTarget`) fires from the same origin but toward `currentTarget.position + Vector3.up * 0.5f` without the same direction nudge. These differences mean a bot can detect a target partially behind cover (detection ray clears) but fire into a wall (fire ray blocked). The bot remains in Attack state and keeps firing into the wall every `fireInterval` until the next detection cycle at `detectionInterval` (0.5s).

## DoorController position overwrite

DoorController.Start() unconditionally sets `closedPosition = transform.localPosition`. The editor assigns both `closedPosition` and `openPosition` at creation time. The `openPosition` survives because it's guarded by `if (openPosition == Vector3.zero)` — the editor sets it to a non-zero value. But `closedPosition` is always overwritten to the runtime localPosition, making the editor assignment dead code. This becomes a real bug if any door's localPosition differs at Start from what it was at creation time (e.g., if parenting changes the local-space coordinates).

## Weapon bob snap on stop

Both `HandleRecoilRecover()` and `HandleWeaponBob()` write to `weaponHolder.localPosition`. When moving, bob includes recoil: `weaponHolderOriginalPos + recoilOffset + bobOffset`. When the player stops, `bobTimer` resets to 0 and the bob offset drops to zero instantly — no lerp decay. HandleRecoilRecover takes over as sole writer. The transition snaps the weapon holder position, causing a visible pop.
