# Inventory Variant B with armor vest system

The inventory was redesigned from a 16-slot 4x4 grid (opened with Q) to an 8-slot 4x2 grid (opened with Tab) with an always-visible hotbar, a 3D character model preview panel, and a new armor vest item that introduces a secondary damage-absorption layer in the combat system. The approach splits the work across five files: `InventorySystem` for slot reduction and hotbar state, `Combat` for armor HP math, `CharacterModel` for the Three.js preview scene, `PlaytestMode` for input wiring, and `EditorApp.tsx` for the React UI overhaul.

**Watch for:** Vest cannot be unequipped once worn (no way to re-inventory it) (confirmed). WebGL renderer in `CharacterModel` is never sized to its container and may render at incorrect resolution on varying displays (confirmed). Armor breaks permanently on zero HP with no visual/audio feedback to the player (confirmed).

## High-level view

The inventory shrinks to 8 slots and promotes the hotbar to a first-class concept: `hotbarIndex` and `equippedSlot` are kept in sync throughout all code paths (equipSlot, dropItem, reset, cycleHotbar). Mouse wheel and digit keys 1-8 provide fast slot switching when pointer lock is active. The category filter tabs are removed — with only 8 slots there's nothing to filter.

The combat system gains a flat 50-point armor buffer that absorbs damage before HP. When armor reaches zero it self-destructs (`armorEquipped = false`), but the vest item is already consumed from inventory at equip time, so there's no path to re-equip or recover the protection without finding another vest in the world.

The 3D character model is a standalone `CharacterModel` class that spins up its own `WebGLRenderer`, scene, and camera — entirely separate from the main game renderer. It's instantiated each time the inventory opens and disposed on close. The vest overlay mesh toggles visibility to reflect equip state.

The UI drag-to-equip mechanic uses HTML5 drag-and-drop: dragging a vest item from a slot onto the character model container triggers `equipVest()`. This is the only equip path — there's no click or context-menu alternative for the vest specifically.

<summary>Issues (5)</summary>

1. **Vest is one-way equip** — once dragged onto the character model the vest is removed from inventory and there's no unequip path that returns it. Players lose the item permanently even if armor is still full. Add an unequip interaction (e.g., click vest badge on model) that returns the item to inventory if a slot is free.
2. **CharacterModel renderer fixed at 280x400** — `setSize(280, 400)` ignores devicePixelRatio and the actual container dimensions set by CSS `w-[280px] h-[360px]`. On high-DPI screens the preview will be blurry; the height mismatch (400 vs 360) means 40px of canvas is clipped.
3. **Armor destruction has no player feedback** — when `armorHp` hits zero the boolean flips silently. No sound, no screen flash, no notification. Players may not realize their protection is gone mid-fight.
4. **WebGL context accumulation risk** — each inventory open/close creates and destroys a `WebGLRenderer`. Browsers limit concurrent contexts (typically 8-16). Rapid toggling or a leak in the dispose path could exhaust the budget, causing the main game renderer to lose its context.
5. **Hotbar index not synced in swapSlots** — `swapSlots` updates `equippedSlot` when a swap involves the active slot, but never updates `hotbarIndex`. After a swap involving the active slot, `hotbarIndex` and `equippedSlot` diverge, causing the UI highlight to desync from the actually-equipped item.

## Vest equip is irreversible

`InventorySystem.equipVest()` finds the vest slot, nulls it out, sets `vestEquipped = true`, and fires `onVestEquip`. There is no reverse operation that would return the vest to the inventory. `unequipVest()` exists but only flips the boolean — it doesn't create a new item in a slot. It's called only on death (in `PlaytestMode`), after which the player respawns without the vest anyway. A player who equips the vest at full armor has no way to take it off and hand it to someone else or store it — the item is simply consumed.

```typescript
equipVest(): boolean {
  const vestIndex = this.slots.findIndex(s => s?.id === 'item_vest');
  if (vestIndex < 0) return false;
  this.slots[vestIndex] = null;  // item gone
  this.vestEquipped = true;
  // ...no reverse path puts the item back
}
```

## CharacterModel renderer sizing mismatch

The renderer is hardcoded to 280x400 pixels:

```typescript
this.renderer = new THREE.WebGLRenderer({ alpha: true, antialias: true });
this.renderer.setSize(280, 400);
```

But the CSS container is `w-[280px] h-[360px]` (Tailwind class). The canvas is then styled with `width: 100%; height: 100%`, which CSS-scales the 280x400 canvas into a 280x360 box — slightly squishing the image vertically. On retina displays, `setPixelRatio(window.devicePixelRatio)` is never called, so the canvas renders at 1x and upscales blurrily.

The camera aspect ratio is set to `280 / 400 = 0.7`, but the displayed aspect is `280 / 360 = 0.78`, causing additional minor distortion in the character preview.

## Armor depletion is silent

In `Combat.takeDamage`:

```typescript
if (this.armorHp <= 0) {
  this.armorEquipped = false;
  this.armorHp = 0;
}
```

No sound effect, no notification, no camera shake. The HUD bar simply disappears. In a hectic combat situation a player won't notice the bar vanishing. Contrast this with the `die()` method which plays `soundSystem.playDeath()` and triggers a full UI overlay.

## WebGL context lifecycle

The `useEffect` in `EditorApp.tsx` tied to `ptInventory?.isOpen` creates a new `CharacterModel` (and thus a new `WebGLRenderer`) every time the inventory opens. On close, it calls `dispose()` which calls `renderer.dispose()`. This releases the context, but browser garbage collection of the underlying WebGL context is not instant. If the player rapidly toggles inventory (Tab spam), multiple contexts could briefly coexist. Browsers typically hard-cap at 8-16 simultaneous WebGL contexts per page. Exceeding this would force-lose the oldest context — which could be the main game renderer.

A safer approach: create the `CharacterModel` once on playtest start, reuse it across opens, and only call `render()` when visible.

## hotbarIndex diverges from equippedSlot on swap

`swapSlots` updates `equippedSlot` when it's involved in the swap:

```typescript
swapSlots(from: number, to: number) {
  // ...swap logic...
  if (this.equippedSlot === from) {
    this.equippedSlot = to;
  } else if (this.equippedSlot === to) {
    this.equippedSlot = from;
  }
  // hotbarIndex is never updated here
}
```

After this, `hotbarIndex` still points to the original slot. The hotbar UI uses `hotbarIndex` for the yellow ring highlight, while `onEquip` is driven by `equippedSlot`. The two properties will show different slots as "active" after a drag-swap involving the equipped item.
